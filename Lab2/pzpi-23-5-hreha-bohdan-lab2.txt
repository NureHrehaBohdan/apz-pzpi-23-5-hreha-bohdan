2 ЗАВДАННЯ

     На цій лабораторній роботі потрібно розробити мобільний програмний застосунок для будь-якої поширеної на сьогодні мобільної платформи. Мобільний застосунок повинен бути частиною системи і повинен взаємодіяти з нею. Для реалізації програмного застосунку можна використовувати технології для реалізації програмного забезпечення для мобільних платформ, вказані лектором, а саме Kotlin для Android та Swift для iOS. Звіт повинен містити опис прийнятих інженерних рішень. У ньому повинна бути показана будова мобільного застосунку та його взаємодія з іншими частинами системи.
     Звіт повинен містити:
     - UML діаграму прецедентів (Use Case Diagram);
     - UML діаграму компонент (Component Diagram).
     - UML діаграму діяльності (Activity Diagram);
     - UML діаграму станів (State Diagram).



3 ОПИС ВИКОНАНОЇ РОБОТИ
     3.1 Опис прийнятих інженерних рішень
     
     Мобільний застосунок є ключовою частиною розподіленої системи, яка взаємодіє як із сенсорами пристрою, так і з хмарним сервером. Його архітектура побудована за принципом MVVM, що включає три основні рівні: UI Layer (інтерфейс), Domain Layer (ViewModel та логіка обчислень) і Data Layer (робота з мережею та локальним сховищем). Такий підхід зменшує зв’язність між компонентами та спрощує їх подальший розвиток і заміну.
     Для побудови інтерфейсу використовується Jetpack Compose, що дозволяє створювати реактивний UI. Під час тренування інтерфейс у реальному часі оновлює дані про дистанцію та швидкість залежно від GPS-координат, що надходять від пристрою.
     Мережева взаємодія реалізована за допомогою Retrofit. Для авторизації використовується JWT-токен, який автоматично додається до кожного запиту через Interceptor, що підвищує безпеку та спрощує роботу з API.
     Застосунок взаємодіє з двома основними зовнішніми системами. По-перше, це GPS-модуль пристрою, який надає координати для розрахунку маршруту. По-друге, Backend-сервер, куди після завершення тренування відправляються всі дані сесії у форматі JSON. Сервер зберігає ці дані, обробляє їх і оновлює статистику маршрутів, що дозволяє користувачу переглядати історію своїх тренувань з будь-якого пристрою.
     
     3.2 UML Діаграми
     
     UML-діаграма прецедентів (див. дод. Б.1) відображає функціональні можливості мобільного застосунку Ski Tracker та взаємодію користувача із системою.
     Основним актором є Лижник (користувач), який взаємодіє з системою через мобільний застосунок. Додатковими зовнішніми акторами виступають система геолокації (GPS) та бекенд-сервер, які забезпечують отримання координат та обробку і збереження даних.
     Діаграма охоплює основні функціональні модулі застосунку Зв’язки між актором і варіантами використання показують, які дії доступні користувачу, а зв’язки із зовнішніми системами демонструють інтеграцію застосунку з GPS для отримання координат та з сервером для збереження і отримання даних.
     Далі була розроблена UML-діаграма компонентів (див. дод. Б.2) відображає архітектуру мобільного застосунку Ski Tracker (Android Client) та взаємодію між його основними модулями.
     Архітектура застосунку поділена на три логічні рівні:
     Presentation Layer — відповідає за користувацький інтерфейс та взаємодію з користувачем. Складається з UI-екранів (Compose) та ViewModel, які керують станом інтерфейсу та обробляють дії користувача.
     Domain Layer — містить бізнес-логіку застосунку. Основним компонентом є Location Engine, який відповідає за отримання та обробку GPS-даних під час тренування.
     Data Layer — забезпечує роботу з даними. Включає репозиторії, API-сервіс для взаємодії з бекендом та менеджер локального сховища (DataStore).
     Далі було зроблено діаграму станів тренування (див. дод. Б.4) Дана UML-діаграма станів відображає життєвий цикл тренування у мобільному застосунку «SkiTracker». Вона показує основні стани, через які проходить тренування, а також переходи між ними в залежності від дій користувача.
     Процес починається зі стану, коли тренування ще не розпочато. Після вибору маршруту та запуску тренування система переходить у активний стан, у якому відбувається збір GPS-даних, розрахунок дистанції та швидкості.
     Під час активного тренування користувач може завершити або скасувати сесію. У випадку завершення система формує підсумкові дані та зберігає їх на сервері. Якщо тренування скасовується, накопичені дані не зберігаються.


     3.3. Приклади програмної реалізації
     
     Для організації взаємодії між мобільним застосунком та сервером було створено інтерфейс ApiService. Він містить методи для отримання історії тренувань, збереження нових результатів та видалення існуючих записів. Використання Retrofit дозволяє автоматично формувати HTTP-запити на основі описаних методів.
     
01 package com.example.ski.network
02 
03 import com.example.ski.network.dto.*
04 import retrofit2.http.*
05 
06 interface ApiService {
07     @GET("/user/training/{userId}")
08     suspend fun getTraining(
09         @Path("userId") userId: Long,
10         @Query("page") page: Int,
11         @Query("sort") sort: String = "createdAt,desc"
12     ): ApiResponse<TrainingPageResponse>
13 
14     @POST("/user/training")
15     suspend fun addTraining(
16         @Body body: TrainingSessionDTO
17     ): ApiResponse<TrainingSessionResponse>
18 
19     @DELETE("/user/training/{id}")
20     suspend fun deleteTraining(@Path("id") id: Int): ApiResponse<Void>
21 }
      
     Для реалізації процесу тренування було створено метод startTraining(), який запускає відстеження місцезнаходження користувача через GPS. Під час отримання нових координат виконується обчислення відстані між точками, що дозволяє накопичувати загальну пройдену дистанцію протягом тренування.
     
01 fun startTraining() {
02     isTracking = true
03     distanceMeters = 0.0
04     startTime = Date()
05 
06     val request = LocationRequest.Builder(Priority.PRIORITY_HIGH_ACCURACY, 5000).build()
07 
08     fusedLocationClient.requestLocationUpdates(
09         request,
10         object : LocationCallback() {
11             override fun onLocationResult(result: LocationResult) {
12                 result.lastLocation?.let { location ->
13                     lastLocation?.let { last ->
14                         // Розрахунок відстані між точками
15                         distanceMeters += last.distanceTo(location).toDouble()
16                     }
17                     lastLocation = location
18                 }
19             }
20         },
21         Looper.getMainLooper()
22     )
23 }
      
     Для передачі результатів тренування на сервер використовується клас TrainingSessionDTO. Він містить основні параметри сесії, такі як користувач, маршрут, дистанція та середня швидкість. Це забезпечує єдиний формат обміну даними між клієнтською та серверною частинами системи.
     
01 data class TrainingSessionDTO(
02     val userId: Int,
03     val startTime: String, 
04     val routeId: Int,
05     val distanceKm: Double,
06     val avgSpeedKmh: Double,
07     val status: String
08 )
      
      
      

4 ВИСНОВКИ

     У ході виконання лабораторної роботи було розроблено мобільний застосунок для платформи Android, який є частиною розподіленої інформаційної системи та взаємодіє з серверною частиною через REST API. Для реалізації застосунку було використано мову програмування Kotlin та сучасні інструменти розробки Android.
     Під час проєктування було обрано архітектурний підхід MVVM, що дозволив розділити інтерфейс користувача, бізнес-логіку та роботу з даними. Також було реалізовано механізми роботи з GPS-модулем пристрою для відстеження маршруту та збору статистики тренувань.
     У звіті було побудовано UML-діаграми прецедентів, компонентів, діяльності та станів, які відображають функціональні можливості системи, її внутрішню структуру та логіку роботи. Отримані результати підтверджують можливість ефективного використання мобільних технологій для збору, обробки та збереження даних про тренування користувачів.
