3 ОПИС ВИКОНАНОЇ РОБОТИ
     3.1 Загальні відомості про шаблони (патерни) проєктування
     
     Шаблони (патерни) проєктування — це типові рішення поширених проблем, що виникають під час розробки програмного забезпечення. Вони не є готовим кодом, а представляють собою перевірені підходи до організації структури класів та взаємодії між об’єктами.
     Використання патернів дозволяє:
* підвищити гнучкість програмного забезпечення;
* спростити підтримку та розширення коду;
* повторно використовувати перевірені архітектурні рішення;
* покращити читабельність та масштабованість системи.
     Класифікація GoF (Gang of Four) поділяє патерни на три основні групи:
1. Породжувальні (Creational) — відповідають за створення об’єктів.
2. Структурні (Structural) — визначають способи побудови складних структур.
3. Поведінкові (Behavioral) — описують взаємодію між об’єктами та розподіл відповідальності.
     Патерни широко використовуються при розробці інформаційних систем, вебзастосунків, ігор, мобільних програм та корпоративного програмного забезпечення.
     
     3.2 Опис обраного патерна
     
     Назва патерна: State (Стан)
     Тип шаблона (патерна): Поведінковий (Behavioral)
     Основне призначення: Патерн State дозволяє об’єкту змінювати свою поведінку залежно від внутрішнього стану. При цьому створюється враження, ніби змінюється сам клас об’єкта.
     Основна ідея полягає у винесенні логіки різних станів у окремі класи. Замість великої кількості умовних операторів (if-else або switch) використовується делегування поведінки поточному об’єкту-стану.
     Передумови застосування: 
     Патерн доцільно використовувати у випадках, коли:
* поведінка об’єкта залежить від його стану;
* система містить багато умовних операторів;
* можливе додавання нових станів у майбутньому;
* потрібно спростити підтримку та масштабування коду.
     Переваги:
* дотримання принципу Single Responsibility Principle;
* дотримання принципу Open/Closed Principle;
* усунення великих if-else конструкцій;
* спрощення тестування;
* покращення читабельності коду.
     Недоліки:
* збільшення кількості класів;
* складніша структура проєкту;
* недоцільність використання у дуже простих системах.

     3.3 Структура шаблона (патерна)
     
     Опис структурних частин:
1. State - Інтерфейс, який визначає спільні методи для всіх станів.
2. ConcreteState - Конкретні реалізації станів. Кожен клас містить логіку, характерну лише для певного стану.
3. Context - Основний об’єкт системи, який зберігає посилання на поточний стан та делегує йому виконання операцій.


     Опис взаємодії об’єктів:
     Об’єкт Context містить посилання на поточний State. Під час виклику певної операції Context передає виконання відповідному класу стану. Конкретний стан може змінювати поточний стан Context на інший.

Рисунок 3.1 — UML-діаграма патерна State
     	
     Опис UML-діаграми (див. рис. 3.1):
     На UML-діаграмі зображена загальна структура патерна State та взаємозв’язок між його компонентами.
     Інтерфейс State визначає спільний набір методів для всіх можливих станів системи. Від нього успадковуються класи ConcreteStateA та ConcreteStateB, які реалізують поведінку для конкретних станів.
     Клас Context містить посилання на поточний об’єкт стану через поле state. Під час виконання операцій Context не реалізує логіку самостійно, а делегує її поточному стану.
     У залежності від активного стану поведінка об’єкта Context може змінюватися. Також конкретні стани можуть ініціювати перехід системи до іншого стану шляхом зміни поточного об’єкта State.
     Таким чином патерн State дозволяє уникнути великої кількості умовних операторів та зробити архітектуру системи більш гнучкою і масштабованою.
     
     3.4 Реалізація шаблона (патерна)
     
     Опис реалізації мовою програмування Java
     Для реалізації патерна State було створено систему світлофора. Світлофор може перебувати у трьох станах:
1. RedLight;
2. GreenLight;
3. YellowLight.
     Кожен стан реалізує власну логіку переходу до наступного стану.
     Основні етапи реалізації
     1. Створення базового інтерфейсу
      01 public interface TrafficLightState {
      02
      03     void next(TrafficLight light);
      04
      05     String getColor();
      06 }
     
     У даному інтерфейсі визначаються методи:
* next() — виконує перехід до наступного стану;
* getColor() — повертає поточний колір світлофора.




     2. Реалізація конкретного стану
      01 public class RedLight implements TrafficLightState {
      02
      03     @Override
      04     public void next(TrafficLight light) {
      05         light.setState(new YellowLight());
      06     }
      07
      08     @Override
      09     public String getColor() {
      10         return "Red";
      11     }
      12 }
     
     Клас RedLight реалізує поведінку червоного сигналу світлофора. Після виклику методу next() система переходить у стан GreenLight.
      01 public class TrafficLight {
      02
      03     private TrafficLightState state;
      04
      05     public TrafficLight() {
      06         state = new RedLight();
      07     }
      08
      09     public void change() {
      10         state.next(this);
      11     }
      12
      13     public void setState(TrafficLightState state) {
      14         this.state = state;
      15     }
      16
      17     public String getColor() {
      18         return state.getColor();
      19     }
     4. Демонстрація використання
      01 public class Main {
      02
      03     public static void main(String[] args) {
      04
      05         TrafficLight light = new TrafficLight();
      06
      07         System.out.println(light.getColor());
      08
      09         light.change();
      10
      11         System.out.println(light.getColor());
      12     }
      13 }
     
     Результат виконання програми:
     Red —> Yellow
     У результаті роботи програми світлофор змінює свій стан з червоного на зелений шляхом делегування логіки поточному класу стану.
